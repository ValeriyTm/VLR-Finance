# About project
Суть проекта - сделать пет-проект "VLR Finance" - это финансовая аналитическая платформа. Пет-проект не предполагается деплоить. 

Проект должен быть строго поделен по функционалу, чтобы можно было не все микросервисы / микрофронты запускать за раз, т.к. ноут не потянет много контейнеров одновременно. Т.е. нужно границы функционала явно определить, чтобы я написал некий функционал, запустил нужные контейнеры и приложение работает. Итог: чтобы ноутбук не перегружался, мы делим систему на независимые домены, а каждый домен — это в идеале пара «микрофронтенд + микросервис», которые можно запускать отдельно от других.
Т.к. это демонстрационный проект и никто явно не будет глубоко в файлы заходить для чтения функционала, на первом этапе реализуем функционал в ширину, а не в глубину, т.е. создаем сервисы не с десятком различных методов, а лишь самое ключевое, условно MVP. При этом архитектура должна предусматривать возможность легкого расширения функционала в уже написанных сервисах.

# Services

## Вертикаль 1 (аутентификация)

Микрофронтенд: auth-profile-mf:

• Стек: Next.js App Router (Isolated mode), React Hook Form, @hookform/resolvers/zod.
• Функционал:
	• Виджеты: Форма логина, Форма регистрации, Панель настроек профиля, Таблица активных сессий пользователя.
	• Клиентская валидация полей в реальном времени с помощью Zod-схем.
	• Слой Entities: Управление локальным стейтом сессии (хранение токенов в памяти для мобилок, триггеры для очистки стейта).

BFF Слой в Next.js: app/api/bff/*/auth/*:

• Для Web/PWA (/api/bff/web/auth/*): Паттерн Token Storage BFF. Принимает JSON от бэкенда, вырезает токены и упаковывает их в безопасные, зашифрованные HttpOnly, Secure, SameSite=Strict куки (access_token и refresh_token).
• Для Mobile/Desktop (/api/bff/mobile/auth/*): Тонкий прокси. Пропускает токены в чистом JSON-теле, адаптируя эндпоинт /refresh, который принимает старый refreshToken строго в body запроса.

Микросервис: auth-service:

• Стек: NestJS, PostgreSQL, Prisma ORM, Redis, @nestjs/jwt, @nestjs/throttler, argon2.
• Внутренний функционал:
	• REST API: Регистрация (хэширование паролей через argon2, запись в DB) и Логин.
	• Бизнес Rate Limiting: Защита от брутфорса (@nestjs/throttler + Redis-хранилище).
	• Управление сессиями: Хранение jti (уникальных ID токенов) в Redis. Ротация токенов.
	• Breach Detection: Если прилетает уже использованный ранее Refresh Token, сервис аннулирует всю цепочку сессий в Redis и блокирует доступ.
	• gRPC Сервер: Метод ValidateUserTariff. Синхронно принимает Access Token от других сервисов, проверяет его криптографическую подпись, сверяет статус отзыва в Redis, проверяет/уменьшает счетчик суточных лимитов на ИИ-запросы.

## Вертикаль 2 (Real-time Терминал и Потоковая Аналитика)
Отвечает за обработку высокоинтенсивного потока рыночных данных и визуализацию графиков.

Микрофронтенд: terminal-mf:

• Стек: Next.js App Router, RTK Query (WebSockets/SSE консьюмер), Библиотека графиков.
• Функционал:
	• Виджеты: Real-time интерактивный график котировок, Стакан ордеров (OrderBook), Панель всплывающих уведомлений (Alerts).
	• Слой Entities: Редюсер рыночных тиков с оптимизированным обновлением стейта (High-Frequency updates).

BFF Слой в Next.js: app/api/bff/*/terminal/*:

• Функционал: Открывает HTTP Server-Sent Events (SSE) или WebSocket соединение с фронтендом. Подписывается на внутренние топики Kafka (market-ticks и market-alerts), агрегирует их и транслирует поток данных на клиент.

Микросервис-воркер: ingestor-service:

• Стек: NestJS, ws (WebSocket клиент), паттерн GoF «Стратегия».
• Внутренний функционал:
	• LiveMarketStrategy: Слушает WebSocket биржи Binance (например, пару BTC/USDT) и без обработки пушит сырые тики в топик Kafka market-ticks (acks=1, enable.idempotence=true).
	• MockMarketStrategy: Автономный генератор случайных тиков и транзакций-аномалий для локальной разработки и тестов без интернета. Переключается через .env.

Аналитическая инфраструктура (Big Data инфтраструктура):

• ksqlDB (CEP Анализ): Непрерывно читает топик Kafka market-ticks. Вычисляет скользящую среднюю (SMA) в 1-минутном временном окне. При отклонении цены тика > 2% генерирует событие аномалии в топик Kafka market-alerts (Гарантия Exactly-Once). Нужно написать скрипты инициализации (файлы .sql с командами CREATE STREAM и CREATE TABLE), чтобы они автоматически применялись при старте контейнера.
• Vector Pipeline: Выступает буферизирующим агентом логов и метрик. Вычитывает топик market-ticks из Kafka, собирает данные в пакеты по объему (batch.size=64KB) или времени (linger.ms=500) и делает массовую вставку в ClickHouse.


## Вертикаль 3 (Управление Портфелем и Транзакционный CDC)
Реализует бизнес-логику балансов пользователей, используя паттерн CQRS для разделения нагрузки записи и чтения.

Микрофронтенд: portfolio-mf:

• Стек: Next.js App Router, RTK Query (REST мутации и запросы).
• Функционал:
	• Виджеты: Форма добавления транзакции (покупка/продажа актива), Круговая диаграмма распределения активов (Asset Allocation), Дашборд PnL (Доходности).
	• Интеграция с кнопкой асинхронного экспорта отчетов (отображает статусы BullMQ).

BFF Слой в Next.js: app/api/bff/*/portfolio/*:

• Функционал: Проксирует REST-запросы, автоматически подставляя Access Token из куки (для веба) или заголовка (для мобилок) в запросы к сервисам портфеля и аналитики.

Микросервис 1: portfolio-service (Слой CQRS - COMMANDS):

• Стек: NestJS, @nestjs/cqrs, PostgreSQL (транзакционная OLTP база), Prisma ORM, RabbitMQ.
• Внутренний функционал:
	• CreateTransactionCommandHandler: Принимает команды на изменение активов, проводит валидацию и записывает данные в Postgres с гарантией ACID.
	• Хореографическая Сага: Инициирует распределенную транзакцию при покупке Premium-статуса. Публикует событие portfolio.balance.deducted в RabbitMQ. В случае сбоя на стороне ИИ-сервиса — ловит ошибку и запускает компенсирующую транзакцию (откат списания денег в Postgres).
	• CDC Слой (Debezium): Отдельный контейнер Debezium слушает WAL-логи таблицы транзакций в PostgreSQL, перехватывает инсерты и мгновенно отправляет их в топик Kafka portfolio-cdc (acks=all) для синхронизации с DWH.

Микросервис 2: analytics-service (Слой CQRS - QUERIES):

• Стек: NestJS, @nestjs/cqrs, ClickHouse (аналитическая OLAP база), движок ReplacingMergeTree.
• Внутренний функционал:
	• GetPortfolioAnalyticsQueryHandler: Не трогает PostgreSQL. Делает быстрый raw SQL-запрос в ClickHouse DWH, куда данные транзакций уже притекли через Debezium и Kafka.
	• Кастомный FIFO Алгоритм: Обрабатывает хронологический массив сделок из ClickHouse в памяти Node.js. За линейное время O(N) по времени и O(M) по памяти (на базе структуры данных Очередь) рассчитывает чистую доходность (PnL) портфеля с учетом скользящей средней стоимости при частичных продажах активов.


## Вертикаль 4 (AI-Copilot и Интеллектуальный Поиск)
Управляет ИИ-агентом, RAG-контекстом и динамическим Generative UI интерфейсом.

Микрофронтенд: ai-copilot-mf:

• Стек: Next.js App Router, Vercel AI SDK (хук useChat), Shadcn UI.
• Функционал:
	• Виджеты: Окно чата с ИИ-ассистентом, интерактивные динамические компоненты (таблицы аномалий, wizard ребалансировки), которые рендерятся прямо внутри чата.
	• Слой Entities: Стейт истории сообщений текущей сессии чата.

BFF Слой в Next.js: app/api/bff/*/ai/*:

• Функционал: Проксирует потоковый ответ (HTTP Fetch Stream / Server-Sent Events) от ИИ-сервиса на фронтенд, обеспечивая эффект печатающегося текста и передачу метаданных Generative UI.

Микросервис: ai-copilot-service:

• Стек: NestJS, LangGraph, Ollama (qwen2.5:3b и nomic-embed-text), PostgreSQL + pgvector (отдельная векторная база), Redis, Mem0, Langfuse.
• Внутренний функционал:
	• Входной фильтр: Валидация промпта через Zod + системный промпт (XML-изоляция) для защиты от Prompt Injection.
	• gRPC Клиент: На входе делает быстрый синхронный запрос в auth-service для валидации сессии и списания ИИ-лимитов.
	• Управление Лэйаутом LangGraph (Граф Агента):
		• Нода 1 (Redis Memory): Подтягивает краткосрочную память (последние 10 сообщений сессии из Redis).
		• Нода 2 (Mem0 Memory): Подтягивает долгосрочные факты о привычках инвестора из базы Mem0.
		• Нода 3 (Router): LLM решает: ответить текстом, вызвать RAG-поиск по документам или активировать Tools (gRPC вызовы к портфелю).
		• Нода 4 (RAG pgvector): Переводит запрос в вектор через nomic-embed-text, делает семантический поиск по HNSW-индексу в векторной Postgres (где лежат проиндексированные PDF финансовых отчетов).
		• Нода 5 (Generative UI Builder): Если в ответе нужны данные, подмешивает в поток JSON-маркеры фронтенд-компонентов.
		• Нода 6 (Mem0 Update): Асинхронно после ответа анализирует чат и извлекает новые долгосрочные факты о пользователе в Mem0.
	• Мониторинг: Отправляет телеметрию шагов графа в локальный сервер Langfuse.

## Вертикаль 5 (Фоновые Задачи и Хранилище Экспорта)
Отвечает за тяжелые асинхронные операции и безопасное хранение файлов.

Микрофронтенд / UI-Модуль: reporting-ui (Интегрирован в Портфель):

• Функционал: Кнопка «Скачать PDF-отчет». Опрашивает статус фоновой задачи. При завершении — инициирует скачивание по временной ссылке.

Микросервис: background-jobs-service:

• Стек: NestJS, BullMQ, Redis (ioredis), MinIO (@aws-sdk/client-s3).
• Внутренний функционал:
	• Принимает команду на экспорт от BFF, ставит задачу в очередь BullMQ в Redis и мгновенно возвращает клиенту статус 202 Accepted.
	• BullMQ Воркер: В фоне собирает данные из analytics-service, генерирует файл отчета.
	• MinIO (S3) Интеграция: Загружает файл в полностью закрытый (Private) бакет user-private-data в MinIO, применяя Server-Side Encryption (AES256).
	• Генерирует Presigned URL со сроком жизни 15 минут через S3 SDK и записывает ссылку в статус задачи в Redis для выдачи пользователю.

# Features
1) Регистрация; вход в систему; logout; logoutall (из всех сессий).

2) Действие: Пользователь открывает вкладку торгового терминала, чтобы следить за графиком BTC/USDT.
2.1. Микросервис Ingestor Service (Фоновый воркер): По паттерну «Стратегия» (выбран режим Live) держит открытым WebSocket к бирже Binance. Получает каждую сделку и транслирует тики как продюсер в топик Kafka market-ticks (Гарантия At-Least-Once, enable.idempotence=true).
2.2. Конвейер Стриминга и CEP:
	• ksqlDB: Потоково вычитывает топик market-ticks. На лету считает минутную скользящую среднюю (SMA). Если цена тика отклоняется более чем на 2% от SMA, ksqlDB мгновенно генерирует событие-алерты в топик Kafka market-alerts (Гарантия Exactly-Once).
	• Vector (Log/Data конвейер): Вычитывает топик market-ticks из Kafka, собирает тики в пачки (батчи) по 64KB / 500мс и массово записывает их в ClickHouse (в таблицу ReplacingMergeTree).
2.3. Связь с клиентом:
	• Фронтенд через RTK Query открывает HTTP Server-Sent Events (SSE) или WebSocket-соединение с Web BFF /api/bff/web/terminal/stream.
	• Web BFF подписывается на топики Kafka market-ticks (для графика) и market-alerts (для аномалий) и стримит эти данные в браузер.
2.4. Фронтенд: График котировок перерисовывается на лету. При появлении события из market-alerts всплывает UI-нотификация Shadcn.

3) Пользователь пишет в чат: «Покажи текущие аномалии по BTC и проанализируй их на основе Whitepaper Биткоина».
3.1. Фронтенд: Vercel AI SDK отправляет текстовый запрос через POST /api/bff/web/ai/chat.
3.2. Web BFF: Считывает access_token из куки, декодирует его в памяти (проверяет exp), убеждается, что токен живой, и проксирует запрос в AI Copilot Service с заголовком Authorization: Bearer <token>.
3.3. AI Copilot Service (NestJS):
	• Синхронный gRPC вызов: Сервис делает блокирующий вызов в Auth Service (ValidateUserTariff), передавая строку токена.
	• Auth Service: Проверяет токен по сигнатуре, смотрит в Redis, активна ли сессия, проверяет дневные лимиты ИИ для этой роли, делает декремент лимита в Redis на -1 и возвращает по gRPC OK.
	• Запуск LangGraph (Цикл Агента): AI Copilot поднимает последние 10 сообщений из Redis (краткосрочный контекст) и факты о юзере из Mem0 (долгосрочная память).
	• Ветвление графа (Инъекции + RAG):
		• Защита: Входная нода проверяет текст через регулярки / Zod на prompt injection.
		• Маршрутизатор: Модель qwen2.5:3b понимает, что нужен поиск. Граф идет в ноду RAG.
		• Поиск: Текст запроса переводится в вектор через локальную модель nomic-embed-text. Делается семантический SQL-запрос в PostgreSQL (pgvector) с использованием HNSW-индекса. Извлекаются куски текста из загруженного PDF Whitepaper.
	• Формирование ответа и Generative UI:
		• qwen2.5:3b собирает ответ на основе контекста RAG и долгосрочной памяти.
		• Так как пользователь попросил «показать аномалии», агент добавляет в поток специальный JSON-маркер компонента: { ui-component: "MarketAlertsTable", props: { ticker: "BTC" } }.
3.4. Стриминг ответа: Передача логов выполнения летит в Langfuse (для трейсинга). Сам ответ через HTTP Stream (SSE) транслируется через BFF на фронтенд.
3.5. Фронтенд: С помощью хуков Vercel AI SDK текст чата печатается по буквам, а в конце чат-пузыря вместо сухого текста динамически рендерится интерактивный компонент <MarketAlertsTable /> из Shadcn, который идет в BFF и выводит реальную таблицу аномалий.
3.6. Асинхронный пост-процесс: Отдельный воркер в LangGraph анализирует диалог и обновляет факты о пользователе в Mem0.

4) Действие: Пользователь нажимает на виджете кнопку «Купить Premium-аккаунт за 50$».
4.1. Фронтенд --> BFF --> Portfolio Service: Запрос падает на эндпоинт мутации. Так как у нас внедрен CQRS, запрос обрабатывает CreateTransactionCommandHandler.
4.2. Старт Саги (Шаг 1 - Запись):
	• В транзакционной базе PostgreSQL (Prisma) создается запись о списании 50$ со счета пользователя. Транзакция получает статус PENDING.
	• Portfolio Service публикует в брокер RabbitMQ событие: portfolio.balance.deducted (содержит userId, amount, sagaId).
4.3. Шаг 2 (Обработка в AI-сервисе):
	• AI Copilot Service слушает очередь RabbitMQ, ловит событие portfolio.balance.deducted.
	• Сервис пытается инициализировать долгосрочную память премиум-пользователя в Mem0.
	• Сценарий А (Успех): Память выделена. Сервис отправляет в RabbitMQ событие ai.resources.allocated.
	• Сценарий Б (Сбой - Ollama/Mem0 упали): Сервис отправляет в RabbitMQ событие ai.resources.allocation_failed.
4.4. Шаг 3 (Финал Саги или Компенсирующая транзакция):
	• При Успехе: Auth Service ловит ai.resources.allocated, делает SQL-апдейт в своей БД, меняя роль пользователя на PREMIUM. Сага успешно завершена.
	• При Сбое: Portfolio Service ловит событие ошибки ai.resources.allocation_failed. Включается компенсирующая транзакция: сервис делает возврат 50$ на баланс пользователя в PostgreSQL и меняет статус транзакции на REJECTED. Юзер видит в интерфейсе ошибку «Не удалось активировать ресурсы, деньги возвращены».

5) Действие: Пользователь открывает дашборд аналитики портфеля, чтобы посмотреть графики доходности (PnL).
5.1. Предыстория (CDC Конвейер): Когда в Трейсе 5 (или при обычных сделках) происходят инсерты в таблицу транзакций user_portfolios в PostgreSQL, инструмент Debezium потоково перехватывает WAL-логи Postgres. Он мгновенно транслирует изменения в топик Kafka portfolio-cdc (Гарантия At-Least-Once с acks=all). Оттуда данные перетекают в ClickHouse.
5.2. Запрос пользователя: Фронтенд делает запрос GET /api/bff/web/portfolio/analytics.
5.3. BFF --> Analytics Service: Запрос через API Gateway падает в Analytics Service и обрабатывается с помощью CQRS GetPortfolioAnalyticsQueryHandler.
5.4. Выполнение Алгоритма (FIFO / Big O):
	• Сервис не трогает транзакционный PostgreSQL (OLTP). Вместо этого он делает один молниеносный raw SQL-запрос в аналитический ClickHouse (OLAP) и забирает всю историю сделок пользователя.
	• В памяти Node.js запускается наш кастомный алгоритм FIFO на базе структуры данных Очередь. Алгоритм за линейное время O(N) по времени и O(M) по памяти сопоставляет исторические покупки с продажами и рассчитывает точный чистый PnL с учетом изменения курсов.
5.5. Ответ: Результат расчета возвращается через BFF на фронтенд и рендерится в виде красивых графиков доходности.

6) Действие: Пользователь нажимает на кнопку «Скачать детальный PDF-отчет по портфелю за год».
6.1. Запрос: Фронтенд отправляет команду через BFF в микросервис Portfolio Service.
6.2. Постановка в очередь: Сервис понимает, что генерация отчета за год по тысячам сделок — это тяжелая задача. Он не заставляет пользователя ждать HTTP-ответа, а мгновенно создает задачу в очереди BullMQ в хранилище Redis и возвращает клиенту статус 202 Accepted (Task Created).
6.3. Фронтенд: Показывает пользователю красивый спиннер/лоадер: «Ваш отчет формируется...».
6.4. Асинхронный воркер: Воркер BullMQ просыпается в фоне, обращается по gRPC к Analytics Service, забирает посчитанные данные портфеля, формирует PDF-файл.
6.5. Загрузка в S3 и Безопасность:
	• Сервис берет SDK @aws-sdk/client-s3 и загружает готовый PDF в закрытый бакет user-private-data в MinIO (S3), передавая заголовок серверного шифрования x-amz-server-side-encryption: AES256.
	• Сервис генерирует временную безопасную ссылку (Presigned URL) к этому файлу со сроком жизни 15 минут.
	• Сервис меняет статус задачи в Redis на COMPLETED и записывает туда сгенерированную ссылку.
6.6. Клиентский доступ: Фронтенд (который периодически опрашивал статус задачи через RTK Query) видит смену статуса на COMPLETED, убирает лоадер и подкладывает под кнопку скачивания полученный Presigned URL. Пользователь скачивает зашифрованный файл напрямую из S3.

7) Действие: В системе происходит любое событие (например, AI Copilot выдал ошибку таймаута сети при связи с Ollama).
7.1. Запись лога: Сервис AI Copilot пишет ошибку в стандартный поток вывода stdout / stderr через стандартный логгер NestJS.
7.2. Перехват логов: Агент Vector, запущенный в Docker-окружении (или как DaemonSet в k3s), перехватывает этот поток вывода, парсит JSON-структуру лога, обогащает его метаданными (имя контейнера, timestamp) и отправляет асинхронным пакетом (acks=0, batch.size=64KB) в топик Kafka system-logs.
7.3. Разветвление логов:
	• В Grafana Loki: Vector-консьюмер забирает логи из Kafka и отправляет их в движок Loki, индексируя только теги (service="ai-copilot", level="error"). Разработчик может мгновенно найти этот текст лога в интерфейсе Grafana через LogQL.
	• В ClickHouse: Другой поток из Kafka батчами сливается в ClickHouse. Там данные агрегируются.
7.4. Мониторинг: На основе данных в ClickHouse в Grafana строится график здоровья системы. Если количество ошибок в ClickHouse резко возрастает, Grafana триггерит алерт для инженеров.
